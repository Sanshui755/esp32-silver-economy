> 这份文档带你认识 `esp32-xiaozhi-chat` 仓库里**每一类文件**：它是什么、放在哪、干什么用、谁在调用它。

## 0. 先认识"文件后缀"：不同后缀代表什么

固件工程里同时存在十几种后缀，先把它们分成四类记住：

### 0.1 C/C++ 代码类（项目主体）

| 后缀   | 全称/含义                             | 在项目里的角色                                                                                                |
| ------ | ------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `.h`   | Header，头文件                        | **"说明书"**：放声明——类长什么样、有哪些函数和成员、常量宏。别的文件想使用它，就 `#include` 它                |
| `.cc`  | C++ 源文件（也可写 `.cpp`，含义相同） | **"真正干活的地方"**：函数的具体实现、业务逻辑。项目主体一律用 `.cc`                                          |
| `.cpp` | C++ 源文件                            | 与 `.cc` 完全等价。项目里只有极少数文件使用（如 `boards/common/blufi.cpp`），属于历史习惯，不代表特殊含义     |
| `.c`   | C 源文件（纯 C，不是 C++）            | 用于**直接从芯片厂商 SDK 搬来的底层驱动**（如某些 LCD 控制器驱动、IO 扩展器驱动）。纯 C 文件里不能写 C++ 的类 |

**`.h` 和 `.cc` 为什么成对出现？** 打个比方：`.h` 像餐厅墙上的菜单（告诉你有哪些菜），`.cc` 像后厨（菜实际怎么做出来）。客人（别的代码）只看菜单点菜，不需要进后厨。

**为什么 `.c` 和 `.cc` 混着用？** 小智是 C++ 工程（自己的逻辑用 `.cc`，能用类、继承等高级特性），但乐鑫/芯片厂商提供的某些外设驱动是用纯 C 写的，直接拿来用最省事，于是保留 `.c`。C++ 可以调用 C，反过来则不行。

### 0.2 配置与数据类

| 后缀             | 含义                             | 在项目里的角色                                                                      |
| ---------------- | -------------------------------- | ----------------------------------------------------------------------------------- |
| `.json`          | 结构化数据（键值对、列表）       | 板型描述 `config.json`、多语言文案 `language.json`，由脚本/程序读取，人也能直接编辑 |
| `.yml` / `.yaml` | 另一种结构化配置                 | 只出现在 `main/idf_component.yml`：声明本组件依赖哪些第三方库（组件管理器清单）     |
| `.csv`           | 逗号分隔表格                     | 分区表：规定 Flash 如何切分区，见第 4 章                                            |
| `.ogg`           | 开源音频格式（Opus/Vorbis 编码） | 提示音和多语言语音包，比 MP3 小、无专利费                                           |
| `.py`            | Python 脚本                      | 构建、转换、测试工具，见第 5 章                                                     |
| `.sh`            | Shell 脚本                       | 简单的命令封装（如 MP3 转 OGG）                                                     |

### 0.3 构建系统专用（没有普通代码后缀）

| 名字                | 角色                                                                                                |
| ------------------- | --------------------------------------------------------------------------------------------------- |
| `CMakeLists.txt`    | CMake 的"施工说明书"：收集哪些源文件、去哪里找头文件、如何链接。根目录和 `main/` 各有一个，职责不同 |
| `Kconfig.projbuild` | 配置菜单定义：`idf.py menuconfig` 里看到的所有可选项（板型、OTA 地址、功能开关）都来自它            |
| `sdkconfig.rename`  | 旧配置项 → 新配置项的改名映射，保证老配置文件不会失效                                               |

### 0.4 文档与杂项

| 后缀/名字                      | 角色                                                             |
| ------------------------------ | ---------------------------------------------------------------- |
| `.md`                          | Markdown 文档（你正在看的这种）                                  |
| `.clang-format`                | 代码排版规则（缩进、括号位置），用 `clang-format` 工具自动格式化 |
| `.gitignore` / `.dockerignore` | 告诉 Git / Docker 哪些文件不用跟踪、不用打包                     |
| `Dockerfile`                   | 描述如何用 Docker 构建一个打包好的编译环境                       |
| `.excalidraw` / 图 `.html`     | 本学习过程中生成的音频管线图，不属于官方固件                     |

## 3. `main/`：全部固件代码的家

`main` 在 ESP-IDF 里是一个"组件（component）"，固件的所有自有代码都在这。下面逐区讲解。

### 3.1 顶层文件逐个讲（13 组，共 21 个文件）

#### `main.cc` —— 程序的第一行代码

- 固件真正的入口 `extern "C" void app_main(void)` 在这里。上电、ESP-IDF 启动完毕后，C 运行时调用它。
- 它做的事极少：创建 `Application` 实例，调用 `Application::GetInstance().Start()`，然后自己就结束了（应用逻辑活在 Application 自己创建的任务里）。
- `extern "C"` 的作用：告诉 C++ 编译器"这个函数按 C 的规则命名"，否则 ESP-IDF（C 写的启动代码）会找不到它。

#### `application.h` / `application.cc` —— 应用核心（全项目的大脑）

- 定义 `Application` 类：**Meyers 单例**（`GetInstance()` 返回函数内静态对象，拷贝构造与赋值用 `= delete` 禁止）。
- 持有全部核心成员：状态机 `device_state_machine_`、音频服务 `audio_service_`、协议对象 `protocol_`、OTA、事件组 `event_group_`、后台任务表 `main_tasks_`、MCP 服务器等。
- `Start()`：初始化板子、唤醒显示、建主任务，启动一切。
- `Run()`：主任务永不返回的事件循环——等待 14 个事件位（`MAIN_EVENT_*`），按优先级处理（网络下发音频、发送音频、状态切换、播放完毕……）。
- `Schedule()`：给其他任务/回调使用的线程安全"投递口"——把一段代码连同"行李"（参数）挂进队列并按铃，由主任务取出执行，避免跨线程直接改对象。
- `InitializeProtocol()`：根据 OTA 接口返回的配置，决定本次走 WebSocket 还是 MQTT。
- 还包含按钮事件的线程安全包装、每秒一次的时钟节拍（刷新时间/状态栏）、`TaskPriorityReset`（RAII：临时抬高任务优先级、出作用域自动还原）。

#### `device_state.h` —— 设备状态"词汇表"

- 定义设备全部运行状态的枚举：`kDeviceStateUnknown / Creating* / Idle / Connecting* / Listening / Speaking / Upgrading ...`。
- 它只回答"有哪些状态"，不规定"能不能从 A 变到 B"。

#### `device_state_machine.h` / `.cc` —— 状态转换"交通规则"

- 定义 `DeviceStateMachine`，内部是"当前状态 + 一张合法转换表"。
- `SetState()` 时先查表：合法才放行并返回 true，非法转换直接拒绝（返回 false 并可记录告警）。
- 这就是硬规则"改变运行状态必须走 `Application::SetDeviceState()`"的执行者——Application 不私自改状态，全部委托给它。

#### `mcp_server.h` / `.cc` —— 设备端 MCP 工具服务器

- 实现"设备即 MCP 服务器"：维护工具注册表，每个工具有 **名字 + 描述 + JSON 参数模式 + 回调函数**。
- 内置工具：`self.xxx` 系列（如音频音量、`self.camera.take_photo` 的注册入口在板子侧）。
- 收到云端 JSON-RPC 的 `tools/call` 后，不直接执行，而是把回调**调度到主任务**执行（`Schedule`），再把结果按 JSON-RPC 封好发回。
- 板子（如带摄像头、红外滤镜、舵机的板）通过它 `AddTool()` 扩展自己的能力。

#### `ota.h` / `.cc` —— OTA 激活、检查、升级

开机后与服务器建立的"第一次接触"全在这里，实际身兼三职：

1. **激活/配置下发**：POST 请求 `ota_url`（NVS 里的自定义值优先，否则用编译默认 `CONFIG_OTA_URL`），服务器返回固件信息 **和 WebSocket/MQTT 连接配置**。`HasMqttConfig()` / `HasWebsocketConfig()` 供 Application 选择协议。
2. **版本检查**：`CheckVersion()` 解析返回的 JSON（`firmware.version`、`firmware.url`），决定是否需要升级。
3. **下载刷写**：`Upgrade(firmware_url)` 通过 HTTP 拉取新固件，流式写入另一个 OTA 分区（`ota_0` / `ota_1` 双分区），成功后标记新分区、下次启动生效；启动后若新固件不干活会被自动回滚。
- 请求带一堆识别头：`Device-Id`（MAC）、`Client-Id`（板子 UUID）、`Serial-Number`、`Accept-Language` 等。

#### `settings.h` / `.cc` —— NVS 设置的"保险柜"

- 对 ESP-IDF NVS（Flash 上的键值存储）的 C++ 封装：`SetString/GetString/SetInt/GetInt` 等。
- 全局只有一个命名空间，保存 WiFi 配置、自定义 `ota_url`、音量、各种开关。
- 默认值与 NVS 缺省的处理、变更通知都在这一层。

#### `system_info.h` / `.cc` —— 设备"户口本与体检表"

- 提供 MAC 地址、芯片型号、芯片修订版、IDF 版本、Flash 大小、PSRAM 大小、堆内存空闲量、运行时长、任务信息等查询。
- 激活请求头、屏幕诊断信息、日志里的"remain heap"都来自它。
- 含上电原因（上电/看门狗/硬复位）查询，可用于故障判断。

#### `assets.h` / `.cc` —— 内置音效"点唱机"

- 把编译进固件的提示音（成功、低电量、弹窗、震动、数字语音等）统一装载、按名字提供播放。
- 与 `main/assets/` 目录对应：资源文件在构建时被打包进 Flash，运行时由此模块索引。
- 多语言语音包（欢迎、升级、数字 0–9、错误提示）的路径与选择也归它管。

#### `cjson_utils.h` —— cJSON 使用小工具（纯头文件）

- 对解析网络 JSON 时反复要写的代码做安全封装：安全取字段、判断类型、取数值/字符串带默认值等。
- 目的：减少裸用 `cJSON_GetObjectItem` 后忘记判空导致的崩溃。

#### `CMakeLists.txt`（main 组件）—— 固件"施工说明书"

- 这是构建系统最繁忙的文件：
  - 收集 `main/` 及 `audio/protocols/display/led/boards/common` 的源文件；
  - 按 `CONFIG_BOARD_TYPE_*` 宏**只加入被选中那一块板**的源文件和头文件目录（一次构建恰好一块板）；
  - 按语言、字体、资源（assets）开关选择要打包进 Flash 的内容，并生成资源头文件；
  - 定义编译特性（C++ 标准、include 路径）。
- 板型选择链 `config.json → build.py → Kconfig → CMakeLists → 板级源码` 的最后一环。

#### `Kconfig.projbuild` —— menuconfig 菜单与功能开关大全

- 定义 `idf.py menuconfig` 里 "Xiaozhi Assistant" 菜单下的一切：
  - `OTA_URL`（默认 `https://api.tenclass.net/xiaozhi/ota/`，换自己服务器就改这里）；
  - Flash 资源选择（默认资源/表情资源/自定义/不打包）、自定义资源文件路径；
  - 默认语言选择；
  - **板型 `choice`**：全部 `CONFIG_BOARD_TYPE_*` 选项；
  - 各类功能开关：自定义消息接收、AEC、调试选项等。

#### `idf_component.yml` —— 第三方依赖清单

- 组件管理器（IDF Component Manager）据此自动下载第三方库到 `managed_components/`。
- 内容分三类：
  - **显示/触摸驱动**：ST7796、GC9A01、ILI9341、SH8601、CO5300、ST7701、各触摸芯片（FT5x06、GT911、CST816S 等）；
  - **音频与 AI**：`espressif/esp-sr == 2.4.7`（WakeNet/VAD/AFE 语音识别）、`esp_codec_dev`、`esp_audio_codec`、`esp32-camera`、`esp_video`；
  - **基础设施**：`78/esp-wifi-connect`（配网）、`78/esp-ml307`（4G 模组）、`78/xiaozhi-fonts`（字体）、`lvgl/lvgl ~9.5`、MQTT、LED 灯带、HUB75 矩阵、电池电量估算等。
  - 很多依赖带 `rules: if target in [...]`：只在对应芯片上下载，避免无关芯片背上负担。
- 末尾锁定 `idf: version >= 6.0.1`。

#### `sdkconfig.rename` —— 配置项改名映射

- 每行一对"旧名 新名"，如板型菜单一统后以太网旧选项映射到新选项、`CONFIG_XIAOZ_USE_ETHERNET → CONFIG_XIAOZHI_NETWORK_ETHERNET`。
- 作用：旧的 `sdkconfig` 文件再次加载时自动改用新名，不会因为重命名而丢配置。

### 3.2 `audio/` —— 音频子系统

目录内分"基础三件"加四个子目录。

**基础文件**

| 文件                       | 干什么用                                                                                                                                                        |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `audio_codec.h` / `.cc`    | **音频编解码芯片抽象基类**：定义"读声音、写声音、设置音量/静音、输入输出格式"等统一接口，并管理输入输出采样率、参考通道（AEC 用）。具体芯片子类在 `codecs/`     |
| `audio_engine.h`           | **音频处理引擎抽象接口**（纯头文件）：定义"送入 PCM、取出处理结果、唤醒词/VAD 事件回调"等契约。AFE 与 Lite 两种实现在 `engines/`                                |
| `audio_service.h` / `.cc`  | **音频总调度**：创建 3 个任务（输入/编码解码/输出）、5 个队列（编码/发送/解码/播放等），把芯片、引擎、Opus 编解码器、事件位连起来；含背压（队列满丢最旧帧）策略 |
| `audio_debugger.h` / `.cc` | 音频调试辅助：保存采集/播放数据、统计丢帧与队列水位，配合 `scripts/audio_debug_server.py` 分析                                                                  |
| `fixed_queue.h`            | 定长、线程安全的队列模板（纯头文件），音频各队列的基础设施，满时按策略丢弃                                                                                      |

## 4. `partitions/` —— Flash 分区表

分区表回答："Flash 这块蛋糕切成哪几块、每块多大"。NVS、应用（两个 OTA 槽）、资源/模型分区都由它划定。

| 文件                      | 适用 Flash/场景                                                                                                              |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `v2/16m.csv`              | **16MB（当前默认）**：适用于多数 S3/P4 板                                                                                    |
| `v2/16m_c3.csv`           | 16MB 的 C3 变体（资源布局按 C3 调整）                                                                                        |
| `v2/8m.csv` / `v2/4m.csv` | 8MB / 4MB Flash 的板子                                                                                                       |
| `v2/32m.csv`              | 32MB 大 Flash                                                                                                                |
| `v1/*.csv`                | 上一代分区布局：`16m`（含 `16m_echoear`、`16m_custom_wakeword` 特殊变体）、`8m`、`4m`（含 `4m_esp-hi`）、`32m`。供旧设备兼容 |
| `v2/README.md`            | 分区布局说明                                                                                                                 |

板型在 `config.json` 的 `sdkconfig_append` 里通过 `CONFIG_PARTITION_TABLE_CUSTOM_FILENAME="partitions/v2/16m.csv"` 选择自己用哪张表。换板型烧录前 `erase-flash` 的原因之一，就是新旧分区边界可能不同。

## 9. 串起来：一次开机，文件被使用的顺序

把前面所有分区按"上电时间线"串一遍，用于复习和定位问题：

```text
① Bootloader（ESP-IDF 的二级引导程序，烧在 Flash 引导分区）
      → 初始化最小硬件，跳到应用分区
② main.cc 的 app_main()
      → Application::GetInstance().Start()
③ application.cc Start()
      → boards/common/board.cc：create_board() 选出本次唯一板型工厂（DECLARE_BOARD）
      → 板级 <板子名>.cc 构造函数：
           读自己的 config.h 引脚
           → 初始化 I²C（i2c_device）、按键（button）、屏幕（display/lvgl_display）、
             摄像头（esp32_camera，打印 Camera initialized）、LED（led）
      → settings.cc：从 NVS 读自定义 ota_url 与各类设置
④ ota.cc：POST 激活接口（默认 CONFIG_OTA_URL，来自 Kconfig.projbuild）
      → 收到协议配置与固件版本
⑤ application.cc InitializeProtocol()
      → 按配置创建 protocols/websocket_protocol 或 mqtt_protocol
⑥ audio/ audio_service.cc：创建 3 任务 5 队列
      → codecs/ 具体芯片驱动开始采集/外放
      → engines/ AFE 或 Lite 引擎喂 PCM，wake_words/ 检测"你好小智"
⑦ 唤醒成功 → 主事件循环（application.cc Run）收事件位
      → 上行：PCM → Opus → protocol 发云端
      → 下行：云端音频 → 队列 → 喇叭；JSON → display 显示状态、mcp_server 执行工具
⑧ 需要升级时 → ota.cc 写入另一个分区 → 重启生效/失败自动回滚
```

**定位问题时怎么用这张表**：现象卡在哪一步，就去查对应环节的文件——屏幕不亮查板级实现与 `lvgl_display`；连不上服务器查 `ota.cc` 的激活日志和 `InitializeProtocol`；唤醒不灵查 `engines/afe_audio_engine` 与 `wake_words`。
