# 1. Flash —— 设备的"硬盘"

**比喻**：电脑的机械硬盘。断电后内容不丢（所以叫**非易失性存储**），但**读取任意位置都快，覆盖写入麻烦**——不能像内存一样随便改一个字节，必须先"擦除一整块"再写。

**原理**：ESP32-S3 板上有一颗单独的 Flash 芯片（你的板子是 16MB），通过 SPI 总线连到主芯片。程序就存在里面，CPU 通过**缓存直接映射（XIP, eXecute In Place）**执行 Flash 里的代码——就像硬盘上的程序不用拷到内存就能跑（乐鑫的硬件魔法）。

**在小智里**：OTA 一讲的分区地图就来自 [partitions/v2/16m.csv](partitions/v2/16m.csv)（由 `CONFIG_PARTITION_TABLE_CUSTOM_FILENAME` 指定）——硬盘被"分区表"切成了几个用途不同的区域：

```
0x0000  bootloader（启动程序，不在分区表里）
0x8000  分区表本身
0x9000  nvs(16KB) │ otadata(8KB) │ phy_init(4KB)
0x20000 ota_0(~3.9MB 固件A) │ ota_1(~3.9MB 固件B)
0x800000 assets(8MB 字体/提示音)
```

# 2. NVS —— Flash 里的"键值小仓库"

**比喻**：一个带标签抽屉的收纳柜。放东西时说"抽屉 `wifi` 里，格子 `ssid`，存 `家里路由器`"，取的时候报同样地址就行。不用管东西具体放在 Flash 的哪个字节。

**原理**：NVS（Non-Volatile Storage）是 ESP-IDF 在 Flash 的 `nvs` 分区上实现的**键值数据库**。比文件系统简单得多：没有文件夹、没有路径，只有 `命名空间 → 键 → 值`。自带两个关键本领：

- **磨损均衡**：Flash 每个单元擦写次数有限（约 10 万次），NVS 自动"换着地方写"延长寿命
- **掉电安全**：写到一半断电，旧数据不会坏

**在小智里**：[settings.cc](main/settings.cc) 是它的 C++ 封装。设备用不同"抽屉"（命名空间）分门别类：

| 命名空间                 | 存什么                  | 谁读写                                                                 |
| ------------------------ | ----------------------- | ---------------------------------------------------------------------- |
| `"wifi"`                 | SSID/密码、ota_url      | 配网流程、[ota.cc L46-53](main/ota.cc#L46-L53)                         |
| `"mqtt"` / `"websocket"` | 服务器地址、token、密钥 | OTA 检测时写入（[ota.cc L149-189](main/ota.cc#L149-L189)），协议层读取 |
| `"display"` 等           | 音量、亮度、主题        | 各功能模块                                                             |

**一条项目规则**（AGENTS.md 的"NVS 键是持久化 API"）：一旦某版本固件把 `wifi/ssid` 写进了用户的设备，**改名等于失忆**——新固件读新键名就找不到老密码了。要改必须写迁移代码。

> 记忆锚点：**Flash 是硬盘，NVS 是硬盘上的一格"收纳柜"，分区表是"房间平面图"，bootloader 是"看平面图决定开哪扇门的管家"**。

# 3. Bootloader —— 开机管家

**比喻**：按电源键后、你的程序跑起来之前，有一段"先醒来的管家程序"，负责检查房子、决定用哪个房间、把客人（你的固件）迎进门。

**原理**：ESP32 上电后跑**两级引导**：

```
上电
 ↓
① ROM 固化代码（芯片出厂烧死的，改不了）
   只做一件事：从 Flash 固定位置(0x0)读出第二级 bootloader
 ↓
② 第二级 bootloader（Flash 0x0~0x8000，espressif 提供的组件）
   读分区表 → 读 otadata 指示牌 → 决定从 ota_0 还是 ota_1 启动
   校验镜像完整性 →（必要时回滚）→ 跳转到固件的 app_main()
 ↓
③ 你的固件：app_main() → Application::Initialize() → Run()
```

**在小智里**：OTA 机制其实全发生在 bootloader 手里（详见 [project-walkthrough.md 第四部分](project-walkthrough.md#第四部分深挖-23ota升级机制)）：

- `otadata` 那 8KB 就是"指示牌"——`esp_ota_set_boot_partition()`（[ota.cc L388](main/ota.cc#L388)）只改牌子，真正执行换房的是 bootloader
- **自动回滚**：新固件没自证清白（`PENDING_VERIFY`）就反复崩溃时，是 bootloader 发现异常、改牌子退回旧分区。你的固件自己救不了自己——它都崩了，只能管家来救

所以你永远不用写 bootloader 代码，但必须懂它：**OTA 的可信度全靠这位管家**。

# 4. DMA —— 硬件自动搬运工

**比喻**：搬家时自己一趟趟搬（CPU）vs 雇一辆传送带（DMA）：你只把地址告诉它（从哪到哪、搬多少），它闷头干活，搬完按个铃叫你。

**原理**：DMA（Direct Memory Access）是芯片里独立于 CPU 的搬运电路：

```
CPU 配置：源地址、目标地址、大小 → 启动
CPU 继续干别的（跑任务、做决策）
DMA 悄悄搬数据 → 搬完 → 触发中断/事件"货到了"
CPU 回来取货
```

**为什么音频离不开它**：麦克风每秒要送 16000 份采样。没有 DMA，CPU 要被 16000 次/秒的中断打断，每次只搬 2 字节——CPU 基本别想干别的了。有 DMA，I²S 控制器自动把采样攒进内存的环形缓冲区，攒满一块才通知一次任务。

**在小智里**：音频管线两端都是 DMA（详见 [audio-pipeline-walkthrough.md](audio-pipeline-walkthrough.md)）：

- **上行**：`NoAudioCodecSimplex::Read()`（[no_audio_codec.cc](main/audio/codecs/no_audio_codec.cc)）底层从 I²S 控制器 1 的 DMA 缓冲取数据。audio_input 任务每 10ms 取 160 个采样——取的时候货早被 DMA 搬好了
- **下行**：`Write()` 把解码出的 PCM 塞进 I²S 控制器 0 的 DMA 发送缓冲，DMA 按采样节拍自动推给喇叭

> 记忆锚点：**audio_input/audio_output 任务是"仓管员"，DMA 是传送带，麦克风/喇叭是厂门。** 任务从不亲手搬货，只跟传送带交接。

# 5. I²S —— 音频专用的高速公路

**比喻**：普通总线是"你自己开车运货还得自己看红绿灯"，I²S 是给音频修的**封闭高速公路**——路快，且"节拍器"直接焊死在路里，所有车按拍子走，永不堵车、永不停运。

**原理**：声音是连续不断的样本流（16kHz = 每秒 16000 个采样）。传它有两大要求：

1. **节拍必须精准**——样本以稳定速率到达，忽快忽慢声音就变调卡顿
2. **不能停**——一分钟不眠不休地流

普通总线干不好：I²C 太慢（自行车运集装箱，管屏幕行，传音频不行）；SPI 能跑但要软件自己打拍子。于是工程师发明了音频专用总线 **I²S（Inter-IC Sound）**——把"打拍子"做进硬件电路，只用三根线：

```
ESP32-S3                     麦克风(INMP441)
   SCK ────────────────────── SCK     ← 位时钟：每跳一下传 1 个比特（节拍器）
   WS  ────────────────────── WS      ← 字选择：现在传的是左还是右声道的样本
   DIN ←───────────────────── SD      ← 数据线：样本的比特流从这里流过
```

核心理解：**I²S = 硬件节拍器 + 流水线**。时钟线按固定频率不停跳，数据线在节拍驱动下一个比特一个比特流过——收发双方都不用软件操心"什么时候发下一个"。这也是它和 DMA（上一节）是黄金搭档的原因：**时钟管节拍、DMA 管搬运、CPU 完全解放**——音频管线的两端就是这么搭起来的。

**对比记忆**：

|          | I²C                      | I²S                        |
| -------- | ------------------------ | -------------------------- |
| 修给谁用 | 屏幕等控制类芯片         | 音频芯片                   |
| 特点     | 慢、两根线、一问一答     | 快、三根线、硬件节拍连续流 |
| 你的设备 | OLED（SSD1306，SDA/SCL） | 麦克风 + 喇叭功放          |

**在小智里**：你的板子用两条**独立的** I²S 通道（"单工"方案，引脚定义在 [config.h](main/boards/bread-compact-wifi/config.h)，通道由 [no_audio_codec.cc](main/audio/codecs/no_audio_codec.cc) 的 `i2s_new_channel()` 开辟）：

| 设备     | I²S 控制器 | 三根线                   | 方向               |
| -------- | ---------- | ------------------------ | ------------------ |
| 麦克风   | 控制器 1   | WS=4, SCK=5, DIN=6       | 流进 ESP32（录音） |
| 喇叭功放 | 控制器 0   | BCLK=15, LRCK=16, DOUT=7 | 流出 ESP32（放音） |

单工 = 收发各走各的高速公路，互不干扰（详见 project-walkthrough.md 1.6 声卡部分和 [audio-pipeline-walkthrough.md](audio-pipeline-walkthrough.md)）。

# 6. 采样率 / 位深 —— 声音的"拍照参数"

**比喻**：把连续声波想象成一条起伏曲线。数字化 = 用相机每隔固定时间拍一张"响度快照"：

- **采样率** = 每秒拍几张。你的麦克风是 **16kHz**——每秒 16000 张，能忠实记录 8kHz 以内的声音（奈奎斯特定理），**人声和语音完全够用**
- **位深** = 每张快照的精细度。**16bit** = 响度分 65536 级，和 CD 音质一样

**算一笔账（这就是为什么要 Opus）**：

```
原始码率 = 采样率 × 位深 × 声道数 ÷ 8
        = 16000 × 16 × 1 ÷ 8
        = 32,000 字节/秒 = 每秒 32KB
```

实时对话每分钟光上行就要近 2MB——WiFi 勉强，4G 又花钱又慢。Opus 压缩后只要每秒十几 KB，人耳几乎听不出差别（丢掉了人耳不敏感的细节）。

**在小智里的两个落点**：

1. **帧尺寸**：Opus 按帧压缩。60ms 一帧 ≈ 16000×0.06 = 960 个采样——这就是音频管线"AFE 攒 60ms 再编码"的来源
2. **两端采样率可不同**：服务器 TTS 回传可能不是 16k（比如 24k）。解码器发现与播放器不一致会动态重建、重采样（audio_service 的 `SetDecodeSampleRate`）——对方寄来的照片尺寸不同，播放前先裁成自己的规格

# 7. LVGL —— 屏幕的"装修公司"

**比喻**：直接操作屏幕 = 自己拿笔一个像素一个像素点。LVGL（Light and Versatile Graphics Library）是**装修公司**：你只说"这面墙放一个标签、写'聆听中'、字号 12"，它负责算出每个像素怎么画。

**原理**：嵌入式最流行的开源图形库，三层能力：

```
① 对象层：label(文字)、bar(进度条)、image(图片)、button…
   —— 每个对象有位置/样式/可见性，改属性即可，不用重画
② 布局/事件层：对齐、排列、点击回调
③ 渲染层：定时把所有对象画进一块"画布"（framebuffer 像素数组）
```

关键理解：**LVGL 不碰硬件**。它只负责"把像素算出来"，最后由移植层（esp_lvgl_port）定期调 LVGL 渲染 → 把画布交给屏幕驱动 → I²C 发给 SSD1306。

**在小智里**：你的 128x32 OLED 就是它装修的：

- 板子创建 SSD1306 屏幕对象并交给 LVGL 移植层注册（[oled_display.cc L53-L80](main/display/oled_display.cc#L53-L80)）——"毛坯房交给装修公司"
- [SetupUI_128x32()](main/display/oled_display.cc#L307-L393) 摆家具：左边 32x32 表情画布 + 右边状态栏和字幕标签
- Application 想换文字只说 `display->SetStatus("聆听中…")`，LVGL 自己找时间重画——**改属性 ≠ 立刻刷屏**，LVGL 任务按自己的节拍统一渲染（省电、防撕裂）

**线程规则**：LVGL 不是线程安全的。任何任务想改 LVGL 对象必须先拿 `DisplayLockGuard`（[display.h L104-126](main/display/display.h#L104-L126)）——装修期间锁门，防两个工人同时改一面墙。

# 8. 七个概念的关系图

```
上电 → Bootloader 读 otadata 指示牌 → 从 Flash 的 ota_0/ota_1 启动固件
                      │
                      ▼
固件运行（Flash 里的代码，XIP 直接执行）
 ├─ NVS：从 Flash 的 nvs 分区读写 WiFi/服务器配置
 ├─ I²S：麦克风/喇叭的专用音频总线（硬件节拍器）
 ├─ DMA：音频数据自动搬运（和 I²S 是黄金搭档：时钟管节拍、DMA 管搬运）
 ├─ 采样率/位深：决定音频数据量和音质的"拍照参数"（16kHz/16bit → 32KB/s → Opus 压缩）
 └─ LVGL：把 Application 要显示的文字/表情渲染成像素 → I²C → 你的 128x32 OLED
```

**一句话总结**：Bootloader 决定"从哪跑"，Flash 是"在哪存"，NVS 是"怎么记配置"，I²S 是"音频走哪条路"，DMA 是"数据怎么搬运"，采样率/位深是"声音怎么量化"，LVGL 是"屏幕怎么画"——七个概念合起来，正好覆盖"启动 → 存储 → 音频 → 显示"四条基础链路。
